* The problem

A bookmark has two identity mechanisms and neither is adequate
on its own:

- **The record cons.**  Precise and ~eq~-comparable, and it is
  what ~bookmark-alist~ holds.  Session-scoped: ~bookmark-load~
  builds fresh conses, so a cons cannot be written to disk or
  survive a reload.
- **The name.**  Persists across sessions, but is neither
  unique (duplicates are legal, and bookmark-gt allows them as
  an opt-in) nor stable (~bookmark-rename~ changes it).

Every defect in §Evidence is code that needed an identity which
only existed in the form it could not use at that moment.

Emacs's own ~bookmark.el~ assumes names are unique — its
~bookmark-store~ overwrites on a name match alone, with no
handler or filename check.  bookmark-gt inherited that
vocabulary while narrowing the condition, which is how
~bookmark-gt-same-name-overwrite~ came to describe something it
does not do.

bookmark+ identified the same problem and solved it by
attaching the record to its own name string as the text
property ~bmkp-full-record~.  That substrate does not survive
~substring-no-properties~, ~format~, or ~concat~; ~equal~
ignores text properties, so records differing only in identity
compare as equal; and it requires circular structures in the
bookmark file.  The conclusion drawn here: an identifier must
be a *value in the record*, not metadata on the key.

* Decisions

** Records are truth; names are queries

Records are precise but perishable.  Names are durable but
ambiguous.  The id is the only form that is both — which is the
whole argument for introducing it.

A function that already holds a record must not convert back to
a name to act on it.  Doing so re-enters ~assoc~ and can act on
a different record.  Every defect in §Evidence is an instance.

*** Perishable: the alist can be rebuilt at any command boundary

~bookmark-maybe-load-default-file~ reloads the file when its
mtime has changed, and with ~bookmark-watch-bookmark-file~ set
to ~silent~ it does so without asking:

#+begin_src emacs-lisp
(and (not (time-equal-p new-mtime old-mtime))
     (not (bookmark--watch-file-already-queried-p new-mtime))
     (or (eq 'silent bookmark-watch-bookmark-file) ...))
(bookmark-load (car bookmark-bookmarks-timestamp) t t)
#+end_src

That function runs at the top of ~bookmark-gt-set~
(=bookmark-gt-core.el:1054=), ~bookmark-gt-list~
(=bookmark-gt-list.el:601=), ~bookmark-store~, and others.  A
reload rebuilds every cons, so a record captured beforehand is
an orphan: mutating it writes to something no longer in
~bookmark-alist~, and the write is lost without a diagnostic.
Bookmark files kept in a synchronized directory make this
routine rather than theoretical.

*** The rule is about lifetime, not about memory versus disk

| Reference lifetime                            | Hold   |
|-----------------------------------------------+--------|
| within one uninterrupted operation            | record |
| across a prompt, timer, stored state, or disk | id     |

Exposed today: ~bookmark-gt-list--marks~ keys conses in a hash
held indefinitely, the ~tabulated-list~ IDs are conses,
~bookmark-gt-list-edit-tags~ captures records and then prompts
before mutating, and the auto-update and browser-tabs timers
close over records.

Two corollaries:

- **Mint before holding.**  Ids are best-effort, so a record
  about to be held across time may not have one.  The act of
  making the reference is the minting moment — the same rule
  already agreed for sequences.
- **Do not resolve ids inside tight loops.**  A batch mutation
  over hundreds of records resolves once and works with records
  inside the loop body, or it becomes O(n²).

*** Why the existing bugs have been survivable

Passing a *name* accidentally survives a reload, because a name
re-resolves against the fresh alist.  That is why the
first-match defects below have gone unnoticed: acting on the
wrong record is quieter than acting on an orphaned one.  It is
not an argument for names.

** Reference parameters are polymorphic

A parameter that *refers to an existing bookmark* dispatches on
type.  The dispatch is total: each Lisp type means exactly one
thing, so nothing has to be guessed.

| Argument | Type   | Behavior                                         |
|----------+--------+--------------------------------------------------|
| ~nil~      | —      | no bookmark given; prompt where appropriate      |
| record   | cons   | used directly                                    |
| name     | string | resolved as a query; ambiguity errors or prompts |
| id       | symbol | resolved exactly; see §The identifier            |

Order matters in the implementation: ~nil~ is itself a symbol,
so it must be tested before the symbol branch or every
"prompt me" call resolves as an id lookup.  Same for ~t~.  The
~cond~ runs nil → cons → string → symbol.  This reads as
correct while being wrong if written in any other order.

~nil~ means *absence*, not "a bookmark that does not exist":
commands prompt, and callers for which prompting is
inappropriate (readers running non-interactively, timers)
error rather than block on a minibuffer nobody is watching.

Resolution goes through one helper.  Parameter name stays
simple (~bookmark~, as ~bookmark.el~ uses in ~bookmark-jump~);
the contract lives in the docstring.

~bookmark-gt-create~ is **not** part of this convention.  Its
~NAME~ names a bookmark being created, not one being
referenced.  The sentinel that requests the interactive name
prompt (~bookmark-gt--prompt-name~, =bookmark-gt-core.el:1037=)
carries over to it: ~nil~ means "use the suggested name without
prompting", which is a different contract from the ~nil~ of a
reference parameter.

** An ambiguous name is an error

No implicit first-match.  A name that matches several records
is not an answer to a query.  Interactive callers may resolve
it by prompting, which is an explicit user choice;
non-interactive callers get an error.

Disambiguation cannot prompt with a plain name list —
~completing-read~ cannot distinguish two identical strings.
Candidates must carry distinguishing data and map back to
records; reuse ~bookmark-gt-jump-candidate-format-function~
rather than growing a second formatter.

Location and tags are not always enough.  Two records with the
same name, in the same file, at the same position have
identical values for both — reachable under ~always~, or by
import.  The discriminator is the display name's ~<N>~ suffix
(§Display names are computed, not stored), which is unique by
construction and readable.  The id is not shown: ~todo<2>~
distinguishes as well as ~todo<bgt-20260901T143012-a3f9c2>~ and
reads better.

** Duplicate names are opt-in; the update policy is gone

~bookmark-gt-same-name-overwrite~ retires.  Every attempt to
name it accurately failed because the variable should not
exist: it selected an implicit update that is now an explicit
command (§Create and update are separate commands).

~bookmark-gt-allow-same-name-bookmarks~ *stays*, with a narrowed
contract.  It previously shared the collision decision with the
overwrite flag, which is what made the pair unexplainable —
which flag applied depended on a condition the user could not
see.  Now it answers one question and nothing else consults it:

  *When may ~bookmark-gt-create~ reuse a name that already
  exists?*

| Value                           | Creating with a name already in use                          |
|---------------------------------+--------------------------------------------------------------|
| ~never~                           | always stored as ~NAME<2>~                                     |
| ~different-destination~ (default) | literal name when the destination differs, otherwise ~NAME<2>~ |
| ~always~                          | always stored under the literal name                         |

Refusal is always a ~<N>~ suffix, never an error: ~create~
always succeeds and the user always gets a bookmark.  The
result is reported in every case, because the user typed a name
and got something they did not type — a suffix, or a second
record under that name.

*** Destination means the target, not the position

The buffer or target being bookmarked: ~filename~ for file and
Dired records, ~url~ for URL records.  Two bookmarks in the same
file at different points share a destination.

Compared the way ~bookmark-gt--collision-record~ did it —
~string=~, then ~file-equal-p~ when both files exist — so paths
differing only by a symlink count as the same destination.
Types with neither field (function, kmacro, sequence) compare
as the same destination, so a second one gets a suffix.

Position deliberately does not count.  If it did, pressing the
create key twice in one buffer at different points would read
as two destinations and be permitted, which is the accident
this value exists to catch.

*** Why the default is ~different-destination~

It permits the use case duplicates exist for — the same short
name in each of several projects — and prevents the accidental
duplicate from creating twice in one spot.

It also limits how many users the redesign affects: a user who
never wanted duplicates gets ~todo<2>~ rather than a second
silent ~todo~, so both records stay addressable by name and
none of the first-match hazards in §Evidence reach them.
~always~ is there for anyone who wants same-name-same-file and
accepts the consequences =readme.org= documents.

*** This is not the old collision check returning

Mechanically it is the same comparison.  The reason the old
helper had to go does not transfer: ~same-name-overwrite~ was
unnameable because its trigger was invisible *and* it selected
between two intents, update or create, so the user could not
tell which they would get.  Here the condition selects nothing
about intent — ~create~ always creates — and the value states
the condition in its own name.  The comparison returns as the
implementation of a documented value rather than as a hidden
policy.

*** The create prompt completes over existing names

The name prompt reads with completion over the current bookmark
names, so a collision is visible while typing rather than
reported afterwards.  The suggested name is still inserted as
editable initial input, so ~RET~ on an untouched prompt creates
immediately — the fast path must survive, since creating is the
frequent operation.

*** Why proliferation was a problem worth solving

With ~create~ always creating and no flag, re-bookmarking the
same spot silently accumulates records — clutter in the list
buffer and the jump reader, and duplicates for users who never
wanted them.  The flag plus the completion prompt plus the
report make every duplicate a choice the user made and saw.

Retiring with the overwrite flag: ~bookmark-gt--collision-record~
and ~bookmark-gt--resolve-collision~ — both existed to decide
between updating and creating, which is no longer a decision the
code makes.  The ~NO-OVERWRITE~ / ~C-u~ argument goes with them:
it forced a duplicate, and ~create~ is now the command that
creates.

~bookmark-gt-disambiguate-name~ *stays*.  It produces the
~NAME<2>~ form, which is what ~create~ does when duplicate names
are not allowed.

*** Road not taken

Enforcing unique names would make the name a usable
identifier, and is what ~bookmark.el~ assumes.  Rejected:
duplicate names are a wanted feature (the same short name in
each of several projects), and ~rename~ would still break
references.

** Create and update are separate commands

~bookmark-gt-set~ is *removed*, not renamed.  It merged two
intents, and every attempt to configure or name that merge
failed: the policy variable was unnameable, and a prompt only
relocated the ambiguity into a value name.  The user knows
which intent they have; the command they invoke says it.

| Command              | Meaning                             |
|----------------------+-------------------------------------|
| ~bookmark-gt-create~   | make a new bookmark here            |
| ~bookmark-gt-update~   | this bookmark now lives where I am  |
| ~bookmark-gt-relocate~ | this bookmark's target becomes *this* |

Why this beats a prompt: creating stays as fast as it is today
(no candidate list to escape), the update path gets a reader
where it earns its cost, and no variable decides anything.

*** ~update~ is delete-and-create preserving identity

Everything describing *where* is re-captured; everything
describing *which bookmark this is* carries over:

| Carried over                  | Re-captured                |
|-------------------------------+----------------------------|
| name, ~bookmark-gt-id~          | ~filename~, ~position~, ~url~    |
| ~tags~, annotation              | front/rear context strings |
| ~created~, ~visits~, ~last-visited~ | ~handler~                    |
| ~auto-update~, temp flag        | all type-specific props    |

Re-capturing the whole location side removes type-specific
props that would otherwise go stale — a PDF record's page data,
an org record's ~id~, a Dired record's marks and ls switches.

Mechanically this is ~setcdr~ on the existing cons, not a
delete and push, so ~eq~ identity survives for the list
buffer's ~tabulated-list~ IDs and its ~eq~-keyed marks hash.
That is also why it cannot repeat the tags loss (§Evidence):
the preserved column is explicit.

~update~ does not prompt for tags.  The defect being fixed is
that updating destroyed them; not prompting makes preservation
structural.  Editing tags is its own command, and update should
be cheap — it is the frequent "I moved, point this here"
operation.

Confirm when the type would change (URL bookmark updated to a
file location, say).  Same-type updates, the common case,
proceed without asking.

*** Why ~relocate~ still exists

Not every type has a current location to capture.  URL,
function, kmacro, and sequence bookmarks have no buffer
position to stand in, so ~relocate~ — which reads the new
target as text — is the only way to change them.  It also fixes
a directory's worth of stale paths from the list buffer without
visiting each file.

~update~ signals on those types and names ~relocate~.
~relocate~ edits the existing type's target field and therefore
cannot retype a record; it refuses a target whose type differs,
because ~update~ is where retyping happens deliberately.

*** Naming

~relocate~ keeps its name: ~bookmark-relocate~ is the built-in,
and in ~bookmark.el~ the record-or-name contract is carried by
the *parameter* name (~bookmark-name-or-record~, 24 uses;
~bookmark-name~, 5), never by the function name.

Not ~move~ for the update command — "move" and "relocate" are
synonyms in English while meaning different things here, and
nobody would reliably guess which is which.

Not ~-location-set~ for anything: ~location~ already means the
target — bookmark+'s key for a URL (read by
~bookmark-gt-url-of~), the built-in ~bookmark-location~, and
the list buffer's column heading.

A separate ~-position-set~ is unnecessary: ~update~ covers
position and filename together, which also handles the moved-to
-a-different-file case that a position-only command could not.

The existing ~-set~ names (~bookmark-gt-tags-set~,
~bookmark-gt-auto-update-set~) are Lisp APIs taking a record,
not commands.  Under the polymorphic convention they become
both, which closes a gap: tags are currently editable only from
the list buffer or from Lisp.

** The ~set~ prefix goes with the command

~set~ named the create/update conflation, so every symbol
carrying it is renamed.  There are more than the one command:

| Now                      | Becomes                       |
|--------------------------+-------------------------------|
| ~bookmark-gt-set~          | removed (→ ~-create~ / ~-update~) |
| ~bookmark-gt-set-url~      | ~bookmark-gt-create-url~        |
| ~bookmark-gt-set-function~ | ~bookmark-gt-create-function~   |
| ~bookmark-gt-set-kmacro~   | ~bookmark-gt-create-kmacro~     |
| ~bookmark-gt-set-sequence~ | ~bookmark-gt-create-sequence~   |
| ~bookmark-gt-set-non-file~ | ~bookmark-gt-create-non-file~   |
| ~bookmark-gt-set-temp~     | ~bookmark-gt-temp-set~          |

The four typed commands all create; keeping ~set-~ would name
them after a removed command.  ~C-x r u~ breaks along with
~C-x r m~, so the readme's install snippet changes in two
places, not one.

~set-temp~ moves to ~temp-set~ for consistency with the other
property mutators, ~bookmark-gt-tags-set~ and
~bookmark-gt-auto-update-set~, which already read
~<property>-set~.

*** One creation pipeline, not two

~bookmark-gt-set~ and ~bookmark-gt-set-non-file~ are parallel
implementations today.  Both run the same tail — refine name,
resolve collision, collect tags, attach tags, push, notify —
and differ only in where the record data comes from: buffer
capture versus caller-supplied handler and props.

Every rule being added (the three-value flag, id minting,
reporting the stored name) would otherwise be implemented
twice, and divergence between two copies is how the current
inconsistencies arose.  Extract the tail:

| Layer                                            | Responsibility                                   |
|--------------------------------------------------+--------------------------------------------------|
| ~bookmark-gt--create-record~ (NAME DATA)           | name policy, tags, mint id, push, report, notify |
| ~bookmark-gt-create~                               | capture from buffer, prompt for name             |
| ~bookmark-gt-create-non-file~ (NAME HANDLER PROPS) | build data from handler and props                |
| the four typed commands                          | call ~create-non-file~                             |

~create-non-file~ stays public: ~bookmark-gt-browser-tabs~ calls
it.

** Hooks

*** One change hook, with the operation as an argument

~bookmark-gt-set-after-hook~ is misnamed today independently of
this redesign: ~bookmark-gt--after-mutation~ runs it on *every*
change — tag edits and temp toggles included — from 13 call
sites across four files, not on ~set~.

It becomes:

#+begin_src emacs-lisp
bookmark-gt-record-changed-hook   ; called with (RECORD OPERATION)
#+end_src

OPERATION is one of ~create~, ~update~, ~relocate~, ~tags~,
~temp~, ~auto-update~, ~delete~.  An observer interested in one
operation filters on the symbol.

Why one hook and not per-command hooks: an observer that wants
*any* change would have to register into all of them, which is
the situation the single notifier was introduced to end.
Nothing external registers into these hooks today, so changing
the arity costs nothing now and is awkward after publication.

"Mutation" is not used in the name: it reads as in-place
modification specifically, and this fires on creation too.

*** The two readers are create-specific

They only run while building a new bookmark, so they take the
command's name:

| Now                              | Becomes                             |
|----------------------------------+-------------------------------------|
| ~bookmark-gt-set-name-reader-hook~ | ~bookmark-gt-create-name-reader-hook~ |
| ~bookmark-gt-set-tag-reader-hook~  | ~bookmark-gt-create-tag-reader-hook~  |

~bookmark-gt-update~ runs neither: it keeps the record's
existing name and tags (§Create and update are separate
commands).

** Display names are computed, not stored

A stored name is what the user typed.  When two records share
one, the *display* name distinguishes them with a ~<N>~ suffix
— the same convention ~generate-new-buffer-name~ uses for
buffers that uniquify cannot separate.

~bookmark-gt-display-name~ is the single place this happens.
It is the identity function today, and its docstring already
says it is "retained as an API surface so future changes (e.g.
hiding auto-generated =<N>= suffixes in the list buffer) have a
single place to hook".  Six call sites already route through it
— list buffer, jump reader, cycling, auto-update.

Two properties follow:

- *Nothing machine-generated is persisted by this layer.*  A
  suffix that exists only for display cannot go stale when a
  record is renamed, relocated, or deleted.
- *Completion candidates are unique*, which is what makes two
  same-named records addressable in the jump reader and in the
  ~update~ prompt.  This replaces the earlier proposal to show
  an id fragment as the discriminator: ~todo<2>~ is readable
  where ~todo<bgt-20260901T143012-a3f9c2>~ is not.

Display names are *not* a resolution namespace.  The completion
table maps the display string back to its record directly, so
nothing has to parse a suffix, and a string handed to the
resolver is still a stored name (§Reference parameters are
polymorphic).

The persisted ~<N>~ that ~bookmark-gt-allow-same-name-bookmarks~
writes under ~never~ is a different thing at a different layer:
that one makes the *stored* names differ, so there is nothing
left for the display layer to distinguish.  Uniquification still
applies under ~never~, because duplicates arrive from outside
~create~ — a bookmark+ import, a hand-edited file,
~bookmark-set-no-overwrite~, or a file synced from a machine set
to ~always~.

* The identifier

** Key name: ~bookmark-gt-id~

Not ~id~.  That key is taken: ~org-bookmark-heading~ stores the
org heading ID there (=org-bookmark-heading.el:162=), and its
jump handler depends on it.  27 of 148 records in one live
alist already carry an ~id~ from other tools.  Writing ours
there would overwrite an org heading ID and break the jump.

Namespaced like ~bookmark-gt-browser-tab~.

** Computing the id

An interned **symbol**, prefixed ~bgt-~, whose body is a mint
timestamp plus a hex suffix — the shape already present in
bookmark files carrying ids from other tools (e.g.
~20260630T091111-5386fe~):

#+begin_src emacs-lisp
(intern (format "bgt-%s-%s"
                (format-time-string "%Y%m%dT%H%M%S")
                (substring (secure-hash 'sha1
                                        (format "%s%s%s" (emacs-pid)
                                                (current-time) (random)))
                           0 8)))
#+end_src

*** Why a symbol, not a string

The type *is* the disambiguation.  A bookmark name is always a
string by ~bookmark-store~'s contract (it calls
~copy-sequence~ and ~set-text-properties~ on the name), so a
symbol can never be a name.  That makes the resolver's dispatch
total rather than heuristic — see §Reference parameters are
polymorphic — and removes any need to guess whether a given
string is a name or an id.

Secondary benefits: interned symbols compare with ~eq~ rather
than ~equal~, and a symbol resists ~concat~ and ~substring~,
which reinforces the rule that the id is opaque and must not be
recomputed.

Cost, stated once: symbols are interned and not collected, so
reading a file interns one symbol per bookmark.  Irrelevant at
any realistic size, and bookmark files are user-controlled.

*** The ~bgt-~ prefix is structural, not decorative

It guarantees the printed form reads back as a symbol.  The
timestamp body alone would read as a symbol only because the
~T~ makes it non-numeric — an accident of the format.  Verified
with ~read-from-string~:

#+begin_src text
20260901T143012-a3f9c2       => symbol
12345678                     => integer
bgt-20260901T143012-a3f9c2   => symbol
#+end_src

Without a guaranteed non-numeric leading character, a future
format change to an all-digit body would make ids read back as
integers and fall through the dispatch without an error.

*** The timestamp is mint time, not creation time

For a record minted during a load pass the bookmark may be
years older than its id.  ~created~ holds the real value; the
id must not be read for it.  The timestamp is kept because it
makes ids sortable and legible when reading the file by hand.

*** Collision checking is free

Minting always runs during a full scan of ~bookmark-alist~, so
the pass collects existing ids into a hash and regenerates on a
hit.  Within-file uniqueness is therefore exact rather than
probabilistic, and the entropy in the suffix only has to cover
the cross-file case (importing or merging two files minted
independently), where the same check applies at import time.

Eight hex characters plus the in-pass check leaves no
collision exposure worth reasoning about.  Six would give
roughly 0.07% for 148 records minted in the same second —
small, but there is no reason to accept it when the check costs
nothing.

*** Generation goes behind a seam

The generator is indirected through a variable so tests bind a
deterministic counter-based stub.  Building the seam now is
cheaper than retrofitting one into a hardcoded ~secure-hash~
call later.

*** Non-determinism is deliberate

A content-derived id (hashing name, filename, position) would
make two machines minting the same file agree.  Rejected for
two reasons:

- **It cannot distinguish the case the id exists for.**  Two
  genuinely duplicate records — same name, same file, same
  position — hash identically.  Breaking the tie requires
  folding in the alist index, which is unstable under
  reordering and deletion.
- **An id that looks computable invites recomputation.**  A
  visibly derived id leads someone to write a
  ~bookmark-gt--compute-id~ and compare that instead of reading
  the stored value, which is identity-by-content — the bug
  class being removed here, and what
  ~bookmark-gt--collision-record~ was.  A random id is opaque
  by construction: there is nothing to recompute.

The cost is that two machines minting the same id-less file
before syncing produce different ids for the same record.  The
answer is minting then saving — once either machine writes, the
other sees ids and mints nothing — leaving a merge problem,
which merging two bookmark files already was.

Emacs seeds its RNG per process, so ~(random)~ does not need
~(random t)~; three ~emacs -Q --batch~ runs on 31.1 gave
distinct values.  Hashing ~current-time~ and ~emacs-pid~
alongside it is redundancy, not a requirement.

** Best-effort, never an invariant

Records written by ~bookmark.el~, bookmark+, or
~org-bookmark-heading~ will have no ~bookmark-gt-id~.  Records
copied between files can share one.  Any code assuming presence
or uniqueness fails the same way name-based code fails today.

The id is a precision layer over name resolution — *id if
present, else name, error if ambiguous* — not a replacement for
it.

** Visibility

The id is internal plumbing: minted by bookmark-gt, stored by
bookmark-gt, resolved by bookmark-gt, never typed by a user.
The user's query interface remains names.

It is visible in exactly two places:

1. ~bookmark-gt-list-describe-record~, which pretty-prints the
   raw record.  Already true, no work required, and the right
   place for it — present when inspecting a record, absent
   otherwise.
2. The bookmark file, where every record gains a key.  Expected;
   worth an upgrade note.

Deliberately *not* visible: no list-buffer column, no
marginalia annotation, no prompt that asks a user to supply an
id, and not in the disambiguation prompt — candidates that
location and tags cannot separate are distinguished by the
display name's ~<N>~ suffix instead (§Display names are
computed, not stored).

** Dangling and duplicate ids

An id that does not resolve is a *broken reference*, not an
absent one.  Resolution signals an error and never returns nil,
which would let callers treat it as "no bookmark" and continue
— the silent-failure pattern this design removes.

Two failures, two messages: an id matching no record is
dangling; an id matching more than one is ambiguous (possible
because ids are best-effort, so a copied file or a merge can
duplicate one).  The fixes differ, so the diagnostics must.

*** Two moments, two mechanisms

| Moment          | Trigger                         | Mechanism |
|-----------------+---------------------------------+-----------|
| resolution time | jumping a sequence, Lisp call   | ~error~     |
| scan time       | the minting pass over the alist | report    |

Scan time must not error, or one dangling reference makes the
bookmark file unloadable.  The minting pass already walks the
whole alist at load, list refresh, and jump, so it validates
stored references in the same traversal at no extra cost.

For the non-fatal report, follow the existing idiom:
~bookmark-gt-list--missing-file-p~ (=bookmark-gt-list.el:216=)
renders a record whose ~filename~ does not exist in
~bookmark-gt-face-missing-file~.  A dangling bookmark-to-bookmark
reference is the same class of problem and gets the same
treatment — visible in the list buffer, not fatal, discoverable
without running anything.

*** Sequences validate before traversing

A five-member sequence with one dangling member must not jump
four and then fail partway through an action that cannot be
undone.  Members are checked up front, producing one error that
names every missing reference.

*** Deletion is what creates dangling ids

~bookmark-gt-delete~ checks for referrers and reports before
deleting — cheap, since the scan already exists.  It reports
rather than blocks: the user may intend it.

This is a further argument for ~bookmark-gt-delete~ existing at
all.  The built-in ~bookmark-delete~ cannot check referrers,
cannot act on a record, and is the destructive first-match path
documented in =readme.org=.

** Compatibility

Bookmark files are alists; ~bookmark.el~ and bookmark+ ignore
keys they do not know, and bookmark-gt already writes ~created~,
~last-modified~, ~visits~, and ~tags~ that neither understands.
One more key changes nothing for them.

Name text properties are already stripped on store
(=bookmark-gt-core.el:361=, matching ~bookmark-store~).  Today
that removes bookmark+'s identity with nothing to replace it;
with ~bookmark-gt-id~ it becomes a handoff.  A record arriving
with ~bmkp-full-record~ and no id is a natural minting point.

Open: whether dropping ~bmkp-full-record~ affects a file
round-tripping back to bookmark+.  The readme currently
promises files "can be read by bookmark+"; verify before
restating that.

** Minting points

One function, called from the places that already scan the
whole alist:

1. Load (advice on the ~bookmark-load~ path).
2. ~bookmark-gt-list~ refresh — catches records created by
   other backends through ~bookmark-store~.
3. ~bookmark-gt-jump-before-read-hook~ — the third full scan,
   and where a foreign record is most likely first seen.

Steady state must be a no-op scan.  Minting during the list
scan must not notify: ~bookmark-gt-list--entries~ is the
~tabulated-list-entries~ function and redraws are triggered by
~bookmark-gt--after-mutation~, so notifying there is
render → mutate → notify → render.

** Minting must not use the mutation helpers

Write with ~bookmark-prop-set~ directly.  Never
~bookmark-gt--after-mutation~ or ~bookmark-gt--stamp-modified~
(=bookmark-gt-core.el:691=).

Three reasons:

- ~--stamp-modified~ writes ~last-modified~ on every record it
  touches.  A load-time pass would stamp the whole file with
  one timestamp, destroying the real history.  Nothing sorts by
  or displays ~last-modified~ today (only Name and Type
  comparators are registered), so the damage would produce no
  visible symptom until someone adds a modification sort — by
  which point the original values are gone.
- ~created~ is set only when absent
  (=bookmark-gt-core.el:362-365=); minting must preserve that.
- ~--after-mutation~ runs ~bookmark-gt-set-after-hook~, the
  documented third-party extension point.  A load-time pass
  would fire it once per bookmark in the file.

** Persistence

Minted ids must reach disk.  Ids minted per session and
discarded would differ on the next launch, so any stored
reference would dangle — the failure being eliminated,
reintroduced.

Bump ~bookmark-alist-modification-count~ **once, at the end of
the pass, with ~NO-SAVE~** (=bookmark-gt-core.el:298=, whose
~NO-SAVE~ argument exists for batch mutators).  Ids then
persist at the next natural save — the quit prompt, or the
user's next real change — rather than provoking an immediate
write at load, which is what a plain ~--note-modification~
would do via ~bookmark-gt--maybe-auto-save~ when
~bookmark-save-flag~ is non-nil.

Temporary records are minted like any other but must not count
toward the tally: they are excluded from ~bookmark-save~ output,
so counting them would make the file appear modified when
nothing writable changed.

*** Rejected: prompt at load

"Bookmarks were loaded without an id — save?" was considered
and rejected.  It does not happen only once:

- Other packages keep creating id-less records through
  ~bookmark-store~; ~org-bookmark-heading~ does so via
  ~org-capture-last-stored~.
- A decline must be remembered or it re-asks every session.
- A file used from a machine running an older bookmark-gt
  returns id-less.

A prompt worded as a one-time migration becomes recurring.  The
timing is also unsafe: ~bookmark-maybe-load-default-file~ fires
lazily on the first bookmark operation, which may be inside the
jump reader's ~completing-read~ or inside the browser-tabs idle
timer.

** Regenerated records

Browser-tab bookmarks are rebuilt on every refresh.  Minting a
fresh id per rebuild makes any reference to a tab dangle
immediately.  They already carry ~browser-gt-id~, which is the
natural stable seed — identity is domain-specific for some
handlers, not purely generated.

* Evidence

Ten defects found while deriving the above.  They are what
makes these decisions load-bearing rather than stylistic.

Five of them (§Jump and list commands resolve through names)
share one shape: the code *holds the record* and passes
~(car record)~ — the name — to a name-taking function.  That is
the "records are truth" rule stated as a bug class, and it
includes a data-loss path reachable through the primary UI.

** Visit tracking credits the wrong record

=bookmark-gt-core.el:886-893=.
~bookmark-gt--on-jump-record-visit~ passes
~bookmark-current-bookmark~ — a *name* — to
~bookmark-gt-record-visit~, which resolves via ~assoc~.  With
two records sharing a name, every jump to either increments
~visits~ and ~last-visited~ on the first.  The second never
accumulates, so the jump reader's MRU sort
(=bookmark-gt-jump.el:447=) ranks it last permanently.

The record is available: ~bookmark-gt--jump-via-override~
receives ~bookmark-name-or-record~.  Under the ambiguity rule
this path would start erroring on every jump to a duplicated
name unless converted to pass the record.

** Rename tracker mutates a record it did not test

=bookmark-gt-core.el:945-946=:

#+begin_src emacs-lisp
(when (equal (bookmark-gt-filename-of rec) from-abs)
  (bookmark-prop-set (car rec) 'filename to-abs))
#+end_src

Holds ~rec~, tests ~rec~, writes through ~(car rec)~ — the
name.  With duplicates this retargets the first record bearing
that name, which may not be ~rec~, leaving the correct record
stale.

** Overwrite discards tags and annotation

~bookmark-gt--resolve-collision~ deletes the record
(~assoc-delete-all~) and ~bookmark-gt-set~ pushes a freshly
built one.  Verified:

#+begin_src text
BEFORE tags=("alpha" "beta") annot="my note" pos=1
AFTER  tags=nil             annot=nil        pos=20  count=1
#+end_src

Re-setting a bookmark at a new position in the same file loses
its tags and annotation.  This is a live bug on the current
default path, independent of the redesign — the update is
implemented as a create, which is what the whole naming problem
follows from.  ~bookmark-gt-tags-set~ shows the correct model:
~setcdr~ on the existing cons, preserving record identity and
every other property.

** Sequence bookmarks reference members by name

=bookmark-gt-handlers.el:973= stores ~(cons 'sequence
bookmarks)~ where ~bookmarks~ is a list of name strings read
via ~bookmark-completing-read~ — which collapses duplicates, so
a sequence can never reference the second record of a
duplicated name.  Renaming a member breaks the sequence with no
diagnostic.

This is the package's one existing persistent cross-reference,
and it is built on the field with no stability.  Under
~bookmark-gt-id~, sequences should store ids, minting on the
referenced records at the moment the reference is made.

** Jump and list commands resolve through names

Five sites, one shape.  Each holds the record and passes its
name to a name-taking function, which resolves first-match:

| Site                                             | Code                                                |
|--------------------------------------------------+-----------------------------------------------------|
| ~bookmark-gt-jump~ (=jump.el:203,401,417=)           | candidate carries ~'bookmark-gt-name~, not the record |
| ~bookmark-gt-list-jump~ (=list.el:829=)              | ~(bookmark-jump (car record))~                        |
| ~bookmark-gt-list-relocate~ (=list.el:876=)          | ~(bookmark-gt-relocate (car record))~                 |
| ~bookmark-gt-list-rename~ (=list.el:866=)            | ~(bookmark-rename (car record) unique)~               |
| ~bookmark-gt-list-execute-deletions~ (=list.el:817=) | ~(bookmark-delete (car record) t)~                    |

The deletion site is data loss reachable through the primary
UI: flag the second of two records sharing a name, press ~x~,
and the *first* is deleted while the flagged row remains.
~bookmark-gt-allow-duplicate-names~ defaults to ~t~, so nothing
has to be configured to reach it.

The jump reader is the same mistake bookmark+ made, reduced:
identity is carried on the candidate string, but it carries the
*name* rather than the record, so it does not disambiguate at
all.  Both duplicates are listed as separate candidates;
selecting either jumps to the first.

Fixing these does not require ids — only that the commands stop
round-tripping through names.  ~bookmark-delete~ is the one
exception worth checking, since the built-in is name-based.
Independent of the redesign, and a candidate for fixing first.

** List filters persist with no indicator

~bookmark-gt-list--filters~ is written to
~bookmark-gt-list-state-file~ and restored when the buffer is
created.  There is no mode-line or header-line element showing
that a filter is active, so a filter set in one session narrows
the list indefinitely with nothing on screen saying so.

This is the likely cause of the user report that started the
discussion: two bookmarks stored and jumpable, one shown in the
list.  Unrelated to identity, recorded here because it was
found alongside.

* Resolved during design

** How create and update are chosen

This was the open item — whether a single command should
decide between creating and updating, and how.  It is settled
by removing the single command (§Create and update are separate
commands).  The user picks the intent by picking the command,
so nothing has to infer it.

The rejected alternative was one command with a completion
prompt offering existing bookmarks alongside a new-bookmark
candidate.  It would have worked, but it puts a candidate list
in front of the most frequent operation, and it makes a stray
~RET~ under fuzzy matching move a bookmark the user did not
mean to touch.  Two commands cost one keybinding and remove
both problems.

Two constraints identified there still apply, to
~bookmark-gt-update~'s reader:

- Candidates carry their tags and destination, and are ordered
  with bookmarks in the current buffer first — the same set
  ~bookmark-gt-cycle-next~ computes.
- Updating modifies data the user already has, so the
  destination change is reported.

** Sequence migration

Existing sequences store member *names*
(=bookmark-gt-handlers.el:973=).  They are converted to ids at
load time, in the same scan that mints ids (§Minting points):
one traversal, and sequences stop depending on names from the
first launch after upgrading rather than whenever each sequence
happens to be jumped.

A member name that resolves to exactly one record becomes that
record's id.  A duplicated member name has no unambiguous
answer, so it stays a name and is reported.  Sequence members
therefore accept both forms — id preferred, name as legacy —
and a name member resolves under the usual rule: one match, or
an error.

Accepted as minor: the package is unpublished, so the affected
population is one user's file.

* Remaining open question

** Replacing ~bookmark-current-bookmark~

~bookmark.el~ defines it buffer-locally as "name of bookmark
most recently used in the current file", set on store, jump,
and rename, and cleared on delete when it stops resolving.  It
is read as the default name for a new record and as the
completing-read default for several commands.

Two problems:

- It holds a *name*, so every read of it re-enters ~assoc~.
  That is the direct cause of the visit-tracking defect
  (§Evidence): the tracker credits the first record sharing
  the name.
- It is not reliably a name.  ~bookmark-handle-bookmark~ does
  ~(setq bookmark-current-bookmark bookmark-name-or-record)~,
  so after a jump it may hold a record.

Its stated purpose — "to make moving a bookmark forward
through a file easier" — is the create/update conflation this
design removes.  That workflow becomes ~bookmark-gt-update~,
so what remains is a default for that command's reader.

Open: bookmark-gt needs its own buffer-local current-record
tracking for paths that mutate.  That is new state, so it needs
justifying against the records-only invariant — it would be a
process-scoped resource bounded by the buffer's lifetime, the
same category as ~bookmark-gt-list--marks~.  Holding an id
rather than a record would also satisfy the lifetime rule
(§The rule is about lifetime, not about memory versus disk),
since a buffer-local outlives any single operation.

* Migration impact

Tracked in =ChangeLog.org= §Planned.  The items needing work
beyond a changelog line:

- *Every documented keybinding breaks.*  =readme.org='s install
  snippet binds ~C-x r m~ to ~bookmark-gt-set~, and
  =use-package :bind= on a void function fails at init.  The
  readme change is part of the release, not documentation
  catch-up.
- ~bookmark-gt-same-name-overwrite~ has no successor, so
  ~define-obsolete-variable-alias~ cannot cover it.
  ~bookmark-gt-allow-duplicate-names~ is renamed to
  ~bookmark-gt-allow-same-name-bookmarks~ and changes value type
  from a boolean to a symbol, so an alias cannot cover it: the
  old ~t~ / ~nil~ are not valid values of the new type.  Map
  them on read — ~t~ to ~always~, ~nil~ to ~never~ — and warn.
- =readme.org= §Same-name policy is superseded.  Four rules and
  a flag matrix collapse to: ~create~ creates, ~update~ updates,
  names are queries.  The troubleshooting subsection about
  filters and temporary records stays, and the duplicate-name
  warning is rewritten around the flag rather than around the
  defect list.
- The first save after upgrading rewrites nearly every record —
  a new key on all of them, and text properties omitted from
  the 48 names carrying ~bmkp-full-record~ in one live file.
  Worth an upgrade note for anyone version-controlling their
  bookmark file.
